# Learn from the work

1. **Mid-task correction (`correct`):** When the user corrects an action or assumption mid-run, record the rule in project context or `factory-taste` immediately before continuing.
2. **Post-task review (`reflect`):** Review the task outcome, failures, corrections, and evidence. Read relevant existing lessons.
3. Identify recurring causes. Separate facts from hypotheses and taste preferences.
4. Prefer corrections in this order: architecture, types, automated checks, tests, then instructions.
5. Before changing a skill or workflow, define expected behavior, baseline, test cases, and pass criteria. Include a normal case, a failure case, and an approval or permission boundary case.
6. Run the cases with available tools. Record inputs, outputs, limits, and cost when known. Compare with the baseline, report regressions, and adopt only after `PASS: evidence`.

Do not change goals, permissions, budgets, evaluation rules, or deployment targets without authorization.
